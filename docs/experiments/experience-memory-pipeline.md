Create an experiment runner similar to the workflow in src/runner.py but with the following setup:
- step1: when the goal is first received, the first LLM model call is to parse it into a "semantic action graph" (we call the first step "intent extraction"), which may contain multiple independent "intents", where each "intent" is structured as the following JSON:
	- {
	  "text_intent": <user request natural language subsequence which correspunds to an atomic intent>
	  "action": {
	  	"affordance_type": <subclass of ActionAffordance from homeont ontology>,  # (e.g., SetBrightnessCommand, CloseCommand, TurnOnCommand, SetStyleCommand, ...)
	  	"verb": <"set" or "modify"> # "set" is for the setting the attribute controlled by the affordance to a given value, or for actions that have no parameters (e.g. turning on/off, closing/opening)
	  },
	  "target": {
	  	"artifact_type": <subclass of artifact type from homeont ontology>,     # (e.g. AirConditioner, Blinds, Curtain, Light, MediaPlayer, VacuumRobot, ...),
	  	"workspace_type": <subclass of workspace type from homeont ontology>    # (e.g. Balcony, Bathroom, DiningRoom, ...)
	  }
	}
- to do the parsing, the LLM call system prompt will contain the homeont ontology as reference, as well as instructions on the parsing task, that tell the model to do the matching based on concept local names and the rdfs:comment text of each concept.


- step 2: next, the procedure will take each "intent" and try to match it against previous ones using an "experience management engine"
	- the "experience management engine" is an auxiliary module that has the following functionality:
		- it binds a structured intent description with a list of BehaviorTree plans of which it has been part. This means that a BehaviorTree leaf node corresponds to the structured intent. More technically, the binding will be to a JSON-IR representation of the BehaviorTree node where the intermediate representation is obtained deterministically from the BehaviorTree semantics
			- The BehaviorTree leaf nodes should be a subclass of those in behavior_trees/affordance_nodes.py and should have the ability to automatically extract a JSON-IR based representation from the node directly;
			- We also need a deterministic method that transforms a BehaviorTree generated by the planning module in a JSON-IR representation, by leveraging the semantics of control nodes (sequence, parallel, selector) and leaf nodes (see previous point)

		- it will match two structured intents (one from a new user query with one existing in the memory engine) using a hybrid approach:
			- a sentence-embedding based text similarity between corresponding "text_intents" (use a preloaded "BAAI/bge-small-en-v15" model via FastEmbed library)
			- a slot-matching approach using the "action" and "target" keys of the structured intent representation
			- the matching process works as follows:
				- first the embedding based similarity filters through all intents that have a >= 0.85 match in cosine-based vector embedding similarity
				- for all retrieved intents, the slot-matching seeks a perfect-fit; 
					- if more than one perfect fit, return the one with the highest embedding similarity; if no perfect hit, return nothing

		- it keeps a record of "infeasible intents" - these are structured intents (modeled as above) for which no support exists in the smarthome (no corresponding artifact_type supporting the determined affordance exists in the determined workspace)
			- when performing intent matching, the "infeasible intents" are part of the search space as all the other, but have no BehaviorTree leaf nodes attached. Instead they are marked as infeasible.

- step 3: for all "structured intents" for which the matching procedure produces a hit:
	- if the intent is matched to an "infeasible" one, it is discarded from further planning
	- if it is feasible, the corresponding JSON-IR representation of the BehaviorTree leaf-node is included in the generation context of the "matched experience" plan generation
		- the "matched experience" plan generation procedure requires you to create a prompt for an LLM call that will have:
			- the "structured intent" representation for each matched feasible intent
			- the corresponding JSON-IR of a previous BehaviorTree Leaf Node that addressed the intent
			- the "current state" of the environment as determined from the "state discovery stage"
		- the "matched experience" plan generator task is to instruct on **using the matched affordance** (JSON-IR BehaviorTree leaf node), but **adapt the parameters of the affordance** in accordance with the "text_intent" part of the intent and the current state of the environment
		- the "matched experience" plan generator has to produce a BehaviorTree output similar to how it's done in the planning/output/python_code.py setup that

- step 4: all "structured intents" for which *no* "matched experience" has occurred (no hit from matching procedure) will go through the current
	pipeline of "discovery" (using agentic_query strategy) -> "planning" (using a "constrained" BehaviorTree code generator similar to what is now in planning/output/python_code.py - PythonCodeGenerator class). The only difference is that the generated BehaviorTrees must have nodes in the style mentioned in step 2 (leaf nodes must have a method to obtain a JSON-IR code representation from the code itself). The output of step 4 is a BehaviorTree instance for the "unmatched experience" intents

- step 5:  concatenate the "matched experience" BehaviorTree with the "unmatched experience" BehaviorTree using a parallel control node with policy set to "success on one"

- step 6: run the BT on the simulator (see execution subfolder) and compare the result to ground-truth expectation:
	- if the ground-truth expected changes (or no change if the ground-truth is marked as "error_input") match to the state of the environment after BT execution, then the test is a success; in this case:
		- use the "experience management engine" to store an assignment from each "structured intent" to its corresponding JSON-IR representation of the BT node representing an ActionAffordance invocation; if the structured intent is *identical* (equal text_intent and equal slot matches) to an already stored one, then do not update the corresponding BT node 
		- for all structured intents which are **correctly** identified as unfeasible (split test sentence by "," to get the individual commands, determine "error input" positions in the list and then check if the command matches to the "text_intent" key of a "structured intent" marked as unfeasible in the planning output) - mark them as unfeasible in the "experence management engine"
	- if the BT exeuction fails or the comparison against ground-truth has errors, do not store anything

  - the time (in seconds) that it takes for the "matched experience" planning to produce its BT
  - the time (in seconds) that it takes the "unmatched experience" planning to produce its BT
  - the time (in seconds) it takes end-to-end - from user request to final BT
