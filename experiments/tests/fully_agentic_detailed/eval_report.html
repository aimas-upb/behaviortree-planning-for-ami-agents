Understanding This Report

Ground Truth: The expected correct behavior from the HomeBench dataset - which actions should be called with what parameters, and what property values should result.

Impossible Request: Test cases where the user asks for something that cannot be done with the available devices. For example, asking to "set brightness to 90" on a light that only has on/off capability (no brightness control). The system should recognize these and not attempt them - success means correctly identifying the request as impossible.

Result Types:

  • Pass (Success) - All expected actions matched, all properties verified correctly
  • Partial (Quantifiable) - Plan executed but with some missing/extra actions or property mismatches
  • Fail - No plan generated, execution failed, or impossible request not detected

Action Matching: Matched = correctly identified action, Missing = expected action not in plan, Extra = unexpected action added to plan.

Property Verification: After execution, we check if device properties match expected values (e.g., temperature is actually 21 after setting it).
